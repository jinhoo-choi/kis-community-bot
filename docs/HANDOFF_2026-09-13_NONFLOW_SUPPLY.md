## 2. 이번에 고친 것 — 날짜 숫자 오탐

정규식 리젝 사유 1위가 `research:근거없는수치['11']` 10건이었다. 실제 본문은 다음과 같다.

- 리서치: `... 9월 11일 해당 리포트를 발간했네요.` ← facts 에 `리포트 발간일: 2026-09-11`
- 공시: `계약 종료일은 2027년 10월 17일입니다.` ← facts 에 `계약 종료일: 2027-10-17`

`claims._metadata_numbers()` 가 **라벨 화이트리스트**(`기준일|공시일|발행일|발간일|...`)로
날짜를 인식했기 때문에, `리포트 발간일`·`계약 종료일` 처럼 앞뒤에 말이 붙은 라벨은
매칭되지 않았다. 그 결과 facts 에 명시된 날짜를 본문이 그대로 인용해도
근거 없는 수치로 리젝됐다.

라벨 대신 **facts 안의 날짜 표기 자체**(`YYYY-MM-DD`, `YYYY년 M월 D일` 등)를 찾아
구성요소를 시점 표기로 허용한다. 기존 라벨 경로는 그대로 둔다.

형식만 맞으면 안 된다. PR 리뷰 지적대로 `관리번호: 2026-99-77` 같은 값이 시점으로
풀리면 본문의 `99` 가 근거 없이 통과한다. 숫자 경계(`(?<!\d)`/`(?!\d)`)를 요구하고,
`datetime.date()` 로 실제 존재하는 날짜인지 확인한 매치만 허용한다.

| 구분 | 변경 전 | 변경 후 |
|---|---|---|
| 인식 방식 | 라벨 화이트리스트 | 라벨 + facts 내 날짜 패턴 |
| 리서치 `9월 11일` | 리젝 | 통과 |
| 공시 `2027년 10월 17일` | 리젝 | 통과 |
| facts 에 없는 `47%` | 리젝 | 리젝 (변화 없음) |

리서치 생성 10건 + 공시 1건이 이 한 가지로 버려지고 있었다. 필터 통과 물량이
리서치에서 12 → 최대 22 수준으로 늘어날 수 있다(상한 추정, 실행으로 확인 필요).

회귀 3건 추가. 전체 `356/356`, 문장틀 14/14, 감사 FAIL 0 / WARN 0, 계약 268/268, E2E 20/20.
