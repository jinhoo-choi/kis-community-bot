# AI 협업 규칙 — R&R과 상호 검토

이 레포는 **Claude와 Codex(ChatGPT)가 번갈아 작업**합니다. 두 AI는 서로를
직접 호출하지 않습니다. 레포가 유일한 연결 매개이고, 사용자가 작업을 지시합니다.

직접 연결하지 않는 이유는 **교차 검증을 잃지 않기 위해서**입니다. 서로 호출하면
한쪽이 틀렸을 때 둘 다 틀립니다. 지금 방식에서는 실제로 다음이 잡혔습니다.

| 잡아낸 쪽 | 놓쳤던 문제 |
|---|---|
| Codex | Batch 600초 대기 후 동기 재호출, 수집 이중 증폭 |
| Claude | `#100` 발송 0건(심사 전건 실패), 규칙 간 계약 충돌 12건 |

---

## 1. 역할 분담 (R&R)

강제 수단은 없습니다. **동시에 같은 파일을 고치면 충돌**하므로 지키는 편이 낫습니다.

### Codex 주담당

| 영역 | 파일 |
|---|---|
| 수집·크롤링·외부 API | `src/sources/*`, `src/crawl.py` |
| 실행 인프라·워크플로 | `.github/workflows/*`, `main.py` 실행 골격 |
| 성능·비용·호출 구조 | `src/llm/*`, 배치·병렬·캐시 |
| 실패 처리·복원력 | 재시도, circuit breaker, fail-closed |
| 계측·통계 | `src/stats.py`, 퍼널 지표 |

### Claude 주담당

| 영역 | 파일 |
|---|---|
| 생성 프롬프트·페르소나 | `src/personas_v2.py`, `src/personas.py` |
| Angle·Claim 설계 | `src/angles.py`, `src/claims.py` |
| 필터·규칙 | `src/filters.py`, `src/rules.py` |
| 심사 기준 | `src/judge.py` |
| 게이트·귀속·배포 판정 | `src/gate.py`, `src/theme_map.py`, `src/decide.py` |
| 콘텐츠 품질 평가 | 생성물 전수 검토, 외부 리뷰 대응 |

### 공동

- `config.py` — 양쪽 다 건드림. **변경 시 인계 문서에 반드시 기록**
- `tests/*`, `tools/audit*.py` — 자기 변경에 대한 회귀는 각자 추가
- `docs/*` — 작업 종료 시 각자 작성

### 경계가 모호할 때

**"왜 이 값이 이래야 하는가"가 품질 판단이면 Claude, 성능·안정성 판단이면 Codex**입니다.

예: `GEN_STAGE_SIZE`는 비용 문제라 Codex, `MIN_JUDGE_SCORE`는 품질 문제라 Claude입니다.

## 2. 작업 전 — 반드시 하는 것

1. `git pull` 후 `docs/STATE.md`를 먼저 읽는다
2. 직전 인계 문서(`docs/HANDOFF_*.md`)의 **불변식 표**를 읽는다
3. 페르소나·Angle·Claim·필터를 건드리면
   [`PERSONA_GENERATION_PROCESS.md`](PERSONA_GENERATION_PROCESS.md)의 현재 계약을 읽는다
4. 상대가 "작업 중"으로 표시한 영역은 건드리지 않는다
5. `./run_tests.sh`를 먼저 돌려 **현재 상태가 깨져 있는지** 확인한다
   - 이미 깨져 있으면 내 변경 탓으로 오인하지 않는다

---

## 3. 작업 후 — 반드시 하는 것

1. `./run_tests.sh` 전체 통과 확인 (푸시 전 필수)
2. 변경마다 **독립 커밋**으로 쪼갠다 — 롤백 단위를 남기기 위해서
3. 커밋 메시지에 **왜 고쳤는지와 실측 근거**를 적는다
   - "실측: 배포 23건 중 open_talk 17건" 처럼 숫자를 남긴다
4. `docs/HANDOFF_<날짜>_<주제>.md` 작성
5. `docs/STATE.md` 갱신

---

## 4. 인계 문서 형식

`docs/HANDOFF_<YYYY-MM-DD>_<주제>.md`

| 섹션 | 내용 |
|---|---|
| 기준 커밋 | 시작점·끝점 SHA |
| **커밋별 변경 + 불변식** | 각 커밋이 **무엇을 깨뜨리면 안 되는지** |
| 동작 변경 | 실패 처리 / 사실 정확성 / 비용·시간 |
| 검증 결과 | 테스트 건수, 감사 결과 |
| **첫 실행에서 볼 항목** | 번호 붙인 체크리스트 |
| 의도적으로 남긴 것 | 안 고친 이유 |
| 롤백 | 커밋 단위 revert 방법 |

**불변식 칸이 가장 중요합니다.** 다음 사람이 "이걸 건드리면 안 되는구나"를 알아야
같은 버그를 재발시키지 않습니다.

## 5. 상호 검토 방법

### 검토는 의무입니다

작업을 넘겨받은 쪽은 **자기 작업을 시작하기 전에** 상대의 직전 변경을 검토합니다.
사용자가 따로 지시하지 않아도 합니다.

### 검토 순서

1. `git log --oneline <직전기준>..HEAD`로 변경 범위 파악
2. 인계 문서의 **불변식**과 실제 코드가 일치하는지 확인
3. `./run_tests.sh` 통과 여부 확인
4. **실행 결과를 본다** — 테스트 통과와 실제 동작은 다르다
   - `data/run_stats.jsonl` 마지막 줄
   - `data/run_log.txt`의 경고 라인
   - `by_kind_funnel`에서 어느 단계가 막혔는지
5. 문제를 찾으면 **고치기 전에 사용자에게 보고**한다

### 검토에서 반드시 보는 것

| 항목 | 확인 |
|---|---|
| 발송 건수 | `sent == 0`이면 워크플로가 success여도 실패다 |
| 단계별 퍼널 | `filter_passed == judge_failed` 같은 전멸 패턴 |
| 수집 경고 | `⚠` 라인이 새로 생겼는지 |
| 규칙 충돌 | 새 규칙이 기존 페르소나·Angle 계약과 모순되는지 |
| 오탐 | "정상 0건" 처리가 실제 장애를 숨기고 있지 않은지 |

### 지적 방식

- **추측하지 말고 실측으로 말한다.** "느낌상 느려졌다"가 아니라 "21.2분 → 5.9분"
- **근거 로그나 데이터를 함께 제시한다**
- **상대 변경을 임의로 되돌리지 않는다.** 사용자에게 보고하고 판단을 받는다
- 단, **명백한 문법 오류·즉시 장애는 바로 고치고 보고**한다

### 지적받았을 때

- 방어하지 않는다. 틀렸으면 실측으로 확인하고 고친다
- **기존 테스트가 잘못된 동작을 기대하고 있었다면 테스트도 함께 고친다**
  (실제 사례: 경쟁사 종목방 배정을 기대하던 테스트가 있었다)
- 되돌릴 때는 **해당 커밋만** revert한다. 여러 변경을 한꺼번에 되돌리지 않는다

## 6. 절대 어기지 않는 규칙

이 레포에서 반복해서 대가를 치른 것들입니다.

| 규칙 | 사고 사례 |
|---|---|
| **추측 금지, 프로브 우선** | 컬럼 인덱스를 추측해 2,743종목 중 3개만 파싱 |
| **한 번에 한 변수** | 여러 개를 같이 바꾸면 효과 귀속 불가 |
| **계측 먼저** | 8회 실행 내내 원인을 못 봄. 로그 추가 후 즉시 해결 |
| **지시는 데이터에 진다** | 프롬프트로 막기보다 입력에서 지운다 |
| **규칙 추가 시 계약 전수 대조** | 수치 선두 금지가 페르소나·Angle 12곳과 충돌 |
| **0건을 정상으로 처리하지 말 것** | 시세 0건을 "정상"으로 넘겨 발송 3건 |
| **테스트 통과 ≠ 정상 동작** | `#100`은 267건 통과에 발송 0건 |

## 7. 품질 판정 기준

**심사 rubric을 바꾸면 그 전후 점수는 같은 척도가 아닙니다.** 평균 `fit` 비교로
품질 개선을 주장하면 안 됩니다.

| 구분 | 지표 |
|---|---|
| 운영 KPI | 유형별 수율, 발송 건수, 실행 시간, API 비용 |
| **품질 KPI** | **담당자 최종 게시율, 게시 전 수정량** |
| 관찰 지표 | 새 `fit` 평균 (추이만, 전후 비교 불가) |

품질 개선을 주장하려면 **동일 소재를 변경 전후 생성기에 돌려 고정 기준으로
블라인드 평가**해야 합니다.

## 8. 사용자에게 보고할 때

- 결론부터. 무엇이 되고 무엇이 안 되는지
- **실측 수치를 함께** 제시
- 판단이 필요한 지점은 선택지와 각각의 대가를 제시하고 **대신 결정하지 않는다**
- 자기 실수는 숨기지 않고 먼저 말한다
